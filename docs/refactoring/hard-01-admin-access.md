# HARD-01 — стабильный вход и выход из админки

Status: `DEV VERIFIED` — локальные проверки, CI и smoke после отправки в dev пройдены;
production PR ожидает проверки и слияния.

Решение владельца (2026-09-23): админкой пользуются только Дмитрий и Аня. Сохраняем
один общий `ADMIN_PASSWORD`, прежний экран с одним полем, те же права и срок cookie
30 дней. Не добавляем персональные аккаунты, MFA, роли, журнал действий, таблицу
сессий или новые переменные окружения. При общем пароле невозможно достоверно
определить, кто из двоих выполнил действие; не представляем существующие данные как
персональный аудит.

## Что было

- [`/admin/auth`](../../src/app/admin/auth/route.ts) проверяет общий пароль и выдаёт
  подписанный `HttpOnly` cookie. Выход удаляет cookie в текущем браузере. Серверный
  механизм авторизации и проверки всех admin API остаётся без изменений.
- При ошибке сети проверка сессии переводила интерфейс в состояние закрытого входа,
  хотя истечение не было подтверждено. Проверка запускалась каждые пять минут, но
  не сразу после возвращения во вкладку.
- Ручное обновление продолжало загрузку журнала даже после неуспешной проверки.
  Запоздалый ответ проверки мог перезаписать результат нового входа или выхода.
- Если промежуточный слой возвращал `401` без JSON, клиент считал это общей ошибкой
  сети и мог не открыть экран повторного входа.

## Изменение в dev

- Сетевой сбой и подтверждённое окончание сессии отображаются по-разному. При
  временном сбое уже открытая админка остаётся на экране, но показывает, что
  проверка недоступна; каждый admin API по-прежнему проверяет cookie на сервере.
- На экране входа есть повторная проверка без повторного ввода пароля. После
  возвращения во вкладку проверка запускается снова; обычный интервал остаётся
  пять минут.
- Ответы старых проверок не перезаписывают более новые действия. Ручное обновление
  загружает данные только после подтверждения сессии. Если ответ на вход или выход
  неясен, клиент сверяет состояние с сервером и не объявляет результат наугад.
- `401` от admin API распознаётся как потеря доступа даже при некорректном теле
  ответа. Сообщения и ненавязчивый индикатор состояния используют существующий
  стиль админки.

## Критерии приёмки перед отправкой

1. Локально проходят форматирование, lint, TypeScript, unit-тесты и сборка.
2. Проверены: вход с общим паролем, ошибочный пароль, истёкшая сессия, временный
   сетевой сбой, повторная проверка, возврат во вкладку, успешный и неясный выход.
3. Нет изменений в `ADMIN_PASSWORD`, cookie, сроке сессии, БД, dev/prod и
   пользовательских сценариях покупок.

Этот шаг улучшает ясность и устойчивость интерфейса. Он **не** делает текущий
cookie индивидуально отзывным: как и раньше, досрочно инвалидировать все такие
сессии можно сменой общего пароля. Этот риск принят для текущего масштаба админки
и не выдаётся за реализованный отзыв отдельных сессий.
